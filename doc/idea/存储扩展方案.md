# 存储层扩展方案

> 核心命题：让数据可以灵活选择存储在前端（IndexedDB）或后端（PostgreSQL/Supabase），
> 且两种模式可共存、可切换。

---

## 一、当前存储全景

```
数据类别            当前存储             访问方式              调用点数量
──────────────────────────────────────────────────────────────────────
Stage（课程）       Dexie (IndexedDB)    db.stages.put()        ~14次
Scene（场景）       Dexie (IndexedDB)    db.scenes.bulkPut()    ~14次
ChatSession（对话）  Dexie (IndexedDB)    db.chatSessions.put()  ~5次
AudioFile（音频）    Dexie (IndexedDB)     Blob 存储              ~5次
ImageFile（图片）    Dexie (IndexedDB)     Blob 存储              ~8次
MediaFile（媒体生成）Dexie (IndexedDB)     Blob + meta           ~2次
GeneratedAgent（智能体）Dexie (IndexedDB)  JSON                   ~2次

Classroom（服务端） JSON 文件             fs.readFile/writeFile  ~2次
Media Blob          未实现               StorageProvider 接口    ~0次
                     (NoopStorageProvider)
```

**问题所在**：62 处 `db.xxx` 直接调用散布在 12 个文件中，且没有抽象层。

```typescript
// lib/data-access/factory.ts
export function createDataAccess(): DataAccessProvider {
  if (typeof window === 'undefined') {
    // 服务端 → PostgreSQL / Supabase
    return createSupabaseDataAccess();
  } else {
    // 浏览器端 → 根据配置选择
    const mode = getStorageMode(); // 'local' | 'remote' | 'hybrid'
    switch (mode) {
      case 'local':  return createDexieDataAccess();
      case 'remote': return createRemoteDataAccess(); // 全走 API
      case 'hybrid': return createHybridDataAccess(); // Dexie + 后台同步
    }
  }
}
```

### 模式 B：StorageProvider 扩展（仅适合媒体 Blob）

当前已有的 `StorageProvider` 接口只覆盖了媒体文件。**扩展它，而不是另起炉灶**：

```typescript
// 当前: lib/storage/types.ts
export interface StorageProvider {
  upload(hash: string, blob: Buffer, type: StorageType, mimeType?: string): Promise<string>;
  exists(hash: string, type: StorageType): Promise<boolean>;
  getUrl(hash: string, type: StorageType): string;
  batchExists(hashes: string[], type: StorageType): Promise<Set<string>>;
}
```

新增实现：

```
lib/storage/
├── types.ts
├── index.ts
└── providers/
    ├── noop.ts              ← 现有空实现
    ├── local-fs.ts          ← 新增: 服务器本地文件系统
    ├── s3.ts                ← 新增: AWS S3 / MinIO
    └── oss.ts               ← 新增: 阿里云 OSS / 其他对象存储
```

```typescript
// lib/storage/providers/local-fs.ts
export class LocalFSStorageProvider implements StorageProvider {
  constructor(private baseDir: string) {}

  async upload(hash: string, blob: Buffer, type: StorageType, mimeType?: string): Promise<string> {
    const dir = path.join(this.baseDir, type);
    await fs.mkdir(dir, { recursive: true });
    const filePath = path.join(dir, hash);
    await fs.writeFile(filePath, blob);
    return `/api/proxy-media/${type}/${hash}`;
  }
  // ...
}
```

| 维度 | 评估 |
|---|---|
| **重构量** | 极小。接口已存在，只需新增实现类 |
| **覆盖范围** | 仅媒体文件，不包括结构化数据（stages, scenes 等）|
| **推荐做法** | ✅ **立即可以做**，作为存储扩展的第一步 |

### 模式 C：混合模式（Hybrid Sync）

前端 Dexie 做主存储，后端 PostgreSQL 做持久化备份/跨设备同步。

```
浏览器                           服务器
┌─────────────────────┐         ┌──────────────────────┐
│  Zustand ←→ Dexie    │         │  PostgreSQL            │
│  (主读写, 极速)      │         │  (权威数据源)          │
│                      │  sync  │                        │
│  Sync Engine         │───────►│  Sync API              │
│  ┌────────────────┐  │  push  │  ┌──────────────────┐  │
│  │ PendingQueue   │──┼───────►│  │ PUT /api/sync    │  │
│  │ ConflictResolver│ │  pull  │  │ GET /api/sync    │──┼──►
│  └────────────────┘  │◄───────│  └──────────────────┘  │  │
│                      │        │                        │  │
│  离线时 Dexie 独立    │        │  在线时定期同步         │  │
│  工作，恢复后同步     │        │                        │  │
└─────────────────────┘         └────────────────────────┘  │
                                                             │
                                  其他设备                    │
                                  浏览器 / 手机              │
                                  ◄──────────────────────────┘
```

```typescript
// lib/sync/engine.ts
export class SyncEngine {
  private queue: PendingMutation[] = [];

  async push(scope: 'stages' | 'scenes' | 'all'): Promise<SyncResult> {
    const localData = await this.collectLocalChanges();
    const res = await fetch('/api/sync', {
      method: 'PUT',
      body: JSON.stringify({ mutations: localData, lastSync: this.lastSyncAt }),
    });
    const serverData = await res.json();
    await this.applyServerChanges(serverData);
    this.lastSyncAt = Date.now();
  }

  async pull(): Promise<void> {
    // 反向同步
  }
}
```

| 维度 | 评估 |
|---|---|
| **复杂度** | 🔴 高。同步顺序、冲突解决、离线队列、增量检测，实现难度大 |
| **用户体验** | 🟢 离线可用，在线自动同步 |
| **适用场景** | 移动端优先 / 弱网环境 / 跨设备使用 |

### 模式 D：远程代理模式（Thin Client）

浏览器端不做持久化存储，所有数据操作都通过 API 调用到后端。

```
浏览器                         服务器
┌─────────────────┐          ┌──────────────────────────────┐
│  Zustand         │          │  Next.js API Routes          │
│  (内存状态)      │  API     │  │                            │
│                  │◄────────►│  ├── /api/courses/*          │
│  ClientAdapter   │          │  ├── /api/scenes/*           │
│  (代替 Dexie)    │          │  ├── /api/chat/*             │
│                  │          │  └── /api/media/*            │
│  无本地持久化     │          │                              │
│  刷新后从服务端   │          │  PostgreSQL + S3             │
│  重新加载         │          │  (唯一数据源)                │
└─────────────────┘          └──────────────────────────────┘
```

```typescript
// lib/data-access/impl/remote/stage-repo.ts
export class RemoteStageRepository implements StageRepository {
  async save(stageId: string, data: StageStoreData): Promise<void> {
    await fetch('/api/courses', {
      method: 'PUT',
      body: JSON.stringify({ id: stageId, ...data }),
    });
  }

  async get(stageId: string): Promise<StageStoreData | null> {
    const res = await fetch(`/api/courses/${stageId}`);
    return res.ok ? res.json() : null;
  }
  // ...
}
```

| 维度 | 评估 |
|---|---|
| **重构量** | 中。同样需要 Repository 层，但 Dexie 可彻底移除 |
| **离线能力** | ❌ 依赖网络，断网时无法使用 |
| **适用场景** | LMS 集成场景（用户永远在线，后端可控）|

## 三、方案对比

| 维度 | A: Repository | B: StorageProvider | C: Hybrid Sync | D: Remote Proxy |
|---|---|---|---|---|
| **覆盖范围** | 全部数据结构 | 仅媒体 Blob | 全部数据 | 全部数据 |
| **重构量** | 中 (62处) | 极小 (0处) | 大 (同步引擎) | 中 (62处) |
| **离线支持** | ❌ (依赖实现) | ✅ | ✅ (核心卖点) | ❌ |
| **实现复杂度** | 🟢 中 | 🟢 低 | 🔴 高 | 🟡 中 |
| **增量迁移** | ✅ 逐个 repo 切换 | ✅ 立即可用 | ❌ 需要整体 | ✅ 逐个 repo 切换 |
| **测试性** | 🟢 高 | 🟢 高 | 🟡 中 | 🟢 高 |
| **与 LMS 匹配** | 🟢 高 | 🟡 仅媒体 | 🟢 高 | 🟢 最高 |
| **社区接受度** | 🟢 高 | 🟢 高 | 🟡 可能被认为过度设计 | 🟡 偏离离线优先设计 |

## 五、关键决策点

| 问题 | 影响 |
|---|---|
| **需要离线支持吗？** | 是 → 必须保留 Dexie，考虑 Hybrid Sync；否 → Remote Proxy 更简单 |
| **存量用户数据怎么办？** | 存在用户浏览器 IndexedDB 中的历史课程。如果切换到后端，需要提供一次性导入工具 |
| **实时协作需要吗？** | 需要 → Hybrid Sync 冲突解决更复杂；不需要 → 简单很多 |
| **核心用户场景是什么？** | 学生自己用 → local Dexie 就够；学校统一平台 → Remote Proxy 更适合 |

---

## 六、我的建议

> **用模式 A（Repository）做架构底座，模式 B（StorageProvider）做媒体存储，模式 D（Remote）做 LMS 适配。**

原因：

1. **Repository 模式是对上游最友好的改动**——纯内部重构，接口不变，可逐步提交 PR
2. **StorageProvider 已经存在**，扩展它是最低成本获取后端媒体存储能力的方式
3. **如果目标是接 LMS，不需要 Hybrid Sync**——LMS 场景下用户永远在线，Remote Proxy 更简单可靠
4. **62 处调用点看似多，但 AST-grep 可以批量重写**，实际重构工作量可控
