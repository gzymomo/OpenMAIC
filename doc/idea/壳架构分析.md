# "套壳"架构可行性分析

> 核心命题：在不影响 OpenMAIC 上游社区演进的前提下，将其嵌入 LMS

---

## 一、架构前提

### OpenMAIC 当前架构特征（决定"壳"的约束条件）

| 特征 | 对嵌入的影响 |
|---|---|
| **全栈 Next.js App**，非 library/npm 包 | 不能 `npm install` 引入，必须以独立服务或子应用方式运行 |
| **数据主存 IndexedDB**（浏览器端） | LMS 无法直接读取或管理用户数据，需同步/代理机制 |
| **无 API 优先设计**：大量逻辑在 Zustand store + 客户端完成 | 不能仅通过调用 API 复用 OpenMAIC 能力 |
| **路由耦合**：`/classroom/[id]`、`/` 等路由由 Next.js App Router 管理 | 嵌入时需处理路由冲突或重写 |
| **Zustand + React Context** 状态管理 | 多实例或跨应用状态隔离需额外处理 |
| **纯客户端生成流程**：generate → IndexedDB → play | LMS 无法拦截或注入自定义逻辑 |
| **AGPL-3.0 许可证** | 套壳项目也必须是 AGPL-3.0，或通过 AGPL 合规方式隔离 |

## 二、四种壳架构方案

### 方案 A：Iframe 嵌入（最轻量）

```
┌──────────────────────────────────────────┐
│             LMS Shell                     │
│  ┌────────────────────────────────────┐  │
│  │  Nav / Sidebar (LMS chrome)        │  │
│  ├────────────────────────────────────┤  │
│  │  ┌──────────────────────────────┐  │  │
│  │  │  <iframe src="OMPage">       │  │  │
│  │  │  postMessage 通信            │  │  │
│  │  └──────────────────────────────┘  │  │
│  └────────────────────────────────────┘  │
│  Dashboard / User Mgmt / Analytics       │
└──────────────────────────────────────────┘

OpenMAIC (独立部署, 未修改)
┌──────────────────────────────────────────┐
│   Next.js App                             │
│   /classroom/[id]  /api/*  ...            │
└──────────────────────────────────────────┘
```

| 维度 | 评估 |
|---|---|
| **上游影响** | ✅ 零修改，直接使用上游发布版本 |
| **集成深度** | ❌ 浅。iframe 内无法共享导航/主题/状态，用户体验割裂 |
| **通信方式** | `postMessage` + URL 参数传 token，有限的双向通信 |
| **共享认证** | 需 OAUTH / SSO token 传递（iframe 跨域受限） |
| **数据互通** | ❌ IndexedDB 在 iframe 内，LMS 无法访问 |
| **路由冲突** | ✅ 无冲突，完全隔离 |
| **SEO** | ❌ iframe 内容不被搜索引擎索引 |
| **移动端** | ❌ iframe 在移动端体验差 |
| **维护成本** | 🟢 极低，几乎为零 |
| **适用场景** | 快速原型验证、"启动按钮"式集成 |

### 方案 B：BFF 代理层（API 级集成）

```
┌──────────────────────────────────────────┐
│  LMS Shell (Next.js 16)                   │
│                                           │
│  app/lms/*          → LMS 页面/API        │
│  app/classroom/[id] → LMS 重写到 OM       │
│                                           │
│  /api/lms/auth/*     → 认证 + RBAC        │
│  /api/lms/courses/*  → 课程管理           │
│  /api/lms/users/*    → 用户管理           │
│  /api/lms/analytics/ → 统计               │
│                                           │
│  /api/om-proxy/*     → 代理到 OpenMAIC    │
│                       (注入 ACCESS_CODE   │
│                        + auth context)    │
│                                           │
│  lib/lms-connector/   → OpenMAIC 数据同步 │
│    ├── classroom-sync.ts   ← 读取 OM JSON │
│    ├── media-sync.ts       ← 媒体迁移     │
│    └── user-bridge.ts      ← 用户映射     │
│                                           │
│  PostgreSQL (LMS 数据)                    │
│    ├── users, roles, enrollments          │
│    ├── courses, assignments, grades       │
│    └── analytics_events                   │
└──────────────────────────────────────────┘

         │ HTTP proxy / data sync
         ▼
┌──────────────────────────────────────────┐
│  OpenMAIC (独立部署, 未修改)              │
│                                           │
│  ACCESS_CODE=shared-secret                │
│  data/classrooms/*.json (持久化课程)      │
│  IndexedDB (客户端)                       │
└──────────────────────────────────────────┘
```

| 维度 | 评估 |
|---|---|
| **上游影响** | ✅ 零修改（只需用 ACCESS_CODE + API 通信） |
| **集成深度** | 🟡 中。LMS 可管理课程元数据，但无法介入课堂播放体验 |
| **关键机制** | ① LMS 生成课程 → 调 OM `/api/generate-classroom` ② OM 将结果写入 `data/classrooms/*.json` ③ LMS 通过 `/api/om-proxy/classroom?id=X` 读取 ④ LMS 将课程元数据同步到自己的 PostgreSQL（course_id, title, subject, grade, owner_id, created_at） |
| **数据模型映射** | `OM 的 classroom (JSON)` → `LMS 的 course (DB)`，通过 `course.external_id = classroom.id` 关联 |
| **媒体处理** | 方案 A：OM 自己 serve 媒体（需 #5 媒体服务完成） 方案 B：LMS 定期同步媒体到自己的存储 |
| **认证桥接** | LMS 用户 → URL 中传递 user_id → OM 课堂中作为 nickname 展示（无法真正登录 OM） |
| **维护成本** | 🟡 中。需维护 proxy 层和同步逻辑，但 OM 侧无侵入 |
| **适用场景** | 中度集成，保留 OM 前端不变，LMS 做外围管理 |

### 方案 C：Monorepo 分包 + 独立部署

```
openmaic-lms/
├── apps/
│   ├── openmaic-core/     ← 上游的 git subtree / submodule
│   │   ├── app/
│   │   └── lib/           ← 编译为 npm 包供 lms-shell 使用
│   │
│   └── lms-shell/         ← LMS 应用
│       ├── app/
│       │   ├── lms/       ← 所有 LMS 页面
│       │   └── gateway/   ← 路由网关（统一入口）
│       ├── lib/lms/       ← LMS 业务逻辑
│       ├── packages/      ← LMS 自有包
│       └── pkg.json       ← 依赖 openmaic-core 的编译产物
│
├── packages/
│   └── openmaic-shared/   ← OM 核心类型（手动提取）
│
├── docker-compose.yml     ← lms-shell + openmaic-core + postgres
└── pnpm-workspace.yaml    ← 统一包管理
```

| 维度 | 评估 |
|---|---|
| **上游同步** | 🟡 `git subtree` 或 `git submodule`，上游发版时拉取合并。但 **OpenMAIC 不是 library，合并冲突频繁** |
| **共享代码** | 🟡 可将 OM 的 `lib/types/` 和 `lib/ai/` 等核心逻辑编译为 npm 包，但需大量重构 |
| **路由策略** | 两种方案： ① lms-shell 反代 `/classroom/*` 到 openmaic-core ② 或 lms-shell 直接包含 OM 页面（但需要同步更新） |
| **License** | AGPL-3.0 — monorepo 内两个 app 均需 AGPL |

### 方案 D：OAuth / SSO 深度融合（推荐）

```
User
 │
 ├──► LMS Portal (lms.example.com)
 │     │
 │     ├── /dashboard/*     ← LMS 页面（教师/学生/管理员）
 │     ├── /course/*        ← 课程管理
 │     ├── /analytics/*     ← 统计
 │     │
 │     └── /study/:id       ← 学习入口
 │           │
 │           │  SSO Token (signed JWT, 5min)
 │           ▼
 │    ┌── openmaic.example.com ──────────────────┐
 │    │                                           │
 │    │  middleware.ts                             │
 │    │   ① 验证 JWT (用 LMS 的公钥)               │
 │    │   ② 从 JWT 提取 user_id, nickname, role    │
 │    │   ③ 写入 req.headers (或 cookie)           │
 │    │   ④ 传递给 page/API                       │
 │    │                                           │
 │    │  app/classroom/[id]/page.tsx               │
 │    │   ① 读取 user info → UserProfileStore      │
 │    │   ② 设置 nickname, avatar, gender          │
 │    │   ③ TTS 根据 gender 选择默认声音            │
 │    │   ④ 课堂体验不变                            │
 │    │                                           │
 │    │  app/api/generate-classroom/               │
 │    │   ① 读取 user_id 从 JWT                    │
 │    │   ② 注入到 prompt (个性化)                 │
 │    │   ③ 生成完成后，POST 到 LMS webhook         │
 │    │   ④ LMS 将课程元数据写入自己的 DB            │
 │    │                                           │
 │    │  IndexedDB (每个用户独立)                   │
 │    │  Access Code: 移除或用 LMS token 代替       │
 │    └───────────────────────────────────────────┘
```

| 维度 | 评估 |
|---|---|
| **上游影响** | 🟡 **最小侵入**：需要在上游加约 3 处改动点（见下文 v2） |
| **集成深度** | 🟢 深。用户体验无缝，认证/个性化/回传完整 |
| **核心机制** | SSO JWT 作为唯一桥接，无共享数据库耦合 |
| **维护成本** | 🟢 低。改动点和耦合面极小 |

#### 对 OpenMAIC 上游的最小改动（v2）

```
改动 1: middleware.ts (新增)
  └─ 可插拔 JWT 验证钩子: validateSSOToken(jwt, publicKey) → userInfo
  └─ 通过环境变量 ENABLE_SSO / SSO_JWKS_URL 控制

改动 2: lib/store/user-profile.ts (扩展)
  └─ 新增: ssoUser?: { id, nickname, role, gender }
  └─ 由 middleware 写入 cookie，前端读取

改动 3: app/api/generate-classroom/ (扩展)
  └─ webhook 配置: GENERATION_WEBHOOK_URL
  └─ 生成完成 → POST { classroomId, userId, metadata }

改动 4: TTS 声音选择 (已有能力扩展)
  └─ 根据 user.gender 选择默认 TTS voice
  └─ 目前已有多种 TTS 供应商，只是没有性别 → 声音映射表
```

**这 4 处改动均为可选、可配置、向下兼容**。上游未开启 SSO 时行为完全不变。

| 方案 | 上游侵入 | 集成深度 | 用户体验 | 维护成本 | 推荐度 |

## 四、推荐架构：SSO 深度融合（方案 D）

### 部署架构

```
                          ┌─────────────┐
                          │  PostgreSQL  │
                          │  (LMS 数据)  │
                          └──────┬──────┘
                                 │
┌────────────────────────────────┼──────────────────────────┐
│  LMS (lms.example.com)        │                          │
│  Next.js / Django / Rails     │                          │
│                                │                          │
│  /dashboard/*                  │                          │
│  /admin/*                      │                          │
│  /api/lms/*                    │                          │
│                                │                          │
│  SSO Token Generator ──────┐   │                          │
└─────────────────────────────┼───┘                          │
                              │                              │
                   JWT (signed by LMS)                       │
                              │                              │
┌─────────────────────────────┼──────────────────────────┐  │
│  OpenMAIC (om.example.com)  │                          │  │
│  Next.js 16                 │                          │  │
│                              │                          │  │
│  ① middleware 验证 JWT      │                          │  │
│  ② 提取 user_info           │                          │  │
│  ③ 课堂个性化 + TTS         │                          │  │
│  ④ 生成完成 → webhook → LMS │─────────────────────────┘  │
│                              │  写入 course 到 PostgreSQL │
│  IndexedDB (每个用户独立)    │                          │
│  data/classrooms/*.json      │                          │
└──────────────────────────────┘                          │
                                                          │
                    ┌─────────────────────────────────────┘
                    │
              ┌─────▼──────┐
              │  媒体存储    │
              │  S3/OSS     │
              └────────────┘
```

### 数据流

```
1. 用户在 LMS 点击"开始学习"
2. LMS 生成 JWT { user_id, nickname, role, gender, exp }
3. 302 重定向到 https://om.example.com/classroom/{id}?token={jwt}
4. OpenMAIC middleware 验证 JWT:
   a. 有效 → 写入 cookie，放行
   b. 无效 → 重定向回 LMS
5. 前端读取 cookie → UserProfileStore ← 个性化
6. 用户完成学习 / AI 生成完成
7. OpenMAIC POST webhook → LMS:
   { event: 'classroom_completed',
     classroomId: 'xxx',
     userId: '123',
     subject: 'math',
     grade: 8,
     duration: 1800,
     scenes: 12 }
8. LMS 写入自己的 PostgreSQL
```

### 需要 OpenMAIC 上游做的改动（可作为社区 PR）

这些改动对上游是纯增益（可配置、向下兼容），有合理概率被社区接受：

| 改动 | 价值对上游 | 实现方式 |
|---|---|---|
| **JWT SSO 中间件钩子** | 增加企业级部署场景 | 环境变量 `SSO_JWKS_URL` + `SSO_REQUIRED` |
| **生成完成 webhook** | CI/CD、日志、集成 | 环境变量 `GENERATION_WEBHOOK_URL` |
| **用户信息注入** | 更强的个性化场景 | cookie `om_user_info`（JSON） |
| **TTS 性别映射表** | 更好的默认识别体验 | `DEFAULT_TTS_VOICE_MALE` / `_FEMALE` |

### 你可能需要维护的代码（在壳侧）

```
lms-integration/
├── middleware-overrides/     ← 3 个替换文件
│   ├── middleware.ts         ← +JWT 验证
│   └── ...
├── docker-compose.yml        ← LMS + OM + PostgreSQL + S3
├── nginx.conf                ← 路由 / 反向代理
└── lms-connector/
    ├── jwks-generator.ts     ← 生成 JWK 供双方使用
    ├── webhook-handler.ts    ← 接收 OM webhook
    └── sync-classroom.ts     ← 可选：将 JSON 同步到 DB
```

## 五、关键风险

| 风险 | 等级 | 缓解措施 |
|---|---|---|
| **AGPL-3.0 合规** | 🟢 低 | 壳和 OM 都是 AGPL，只要不闭源销售即合规。AGPL 传染性要求"网络用户"有权获得源代码，但在教育平台内部使用场景通常不构成问题 |
| **OpenMAIC 社区演进方向与 LMS 需求不一致** | 🟡 中 | 将 SSO/webhook 等改动作为**可选功能**提交 PR，降低合并门槛。核心逻辑（生成/课堂播放）大概率不受影响 |
| **IndexedDB 数据无法被 LMS 管理** | 🟡 中 | 对"学习数据"采用混合策略：关键元数据（学了哪些课、时长、成绩）通过 webhook 同步到 LMS DB；详细课堂内容（场景、对话）留在 IndexedDB |
| **课堂播放页面的个性化深度有限** | 🟢 低 | 当前 UserProfile 只能影响 nickname/avatar/voice。如需更深介入（如屏蔽某些功能），需要更多 upstream 改动 |
| **未来 Next.js 升级导致的兼容问题** | 🟢 低 | 双方同为 Next.js 16，同步升级即可 |

## 七、总结

> **"套壳"可行，但不是传统意义的"壳"。推荐 SSO 深度融合模式。**

核心思路不是"在 OpenMAIC 外面包一层"，而是：
1. **OpenMAIC 作为一个独立服务**，专注于它的核心价值（AI 生成 + 课堂播放）
2. **LMS 作为一个独立的门户层**，负责用户管理、权限、课程编排、仪表盘
3. **SSO JWT 作为唯一的桥接点**，两端松耦合
4. **对上游改动控制在 4 处可选配置**，可提交 PR 回馈社区

这样既不影响 OpenMAIC 的社区进化（你的 fork 只需要很小的 diff），又能将 AI 课堂能力干净地嵌入 LMS。
